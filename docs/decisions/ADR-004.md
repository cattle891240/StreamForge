# ADR-004: 内核输出解析策略

## Status

Accepted（2026-09-28）

## Background

N_m3u8DL-RE 是为**交互式终端**设计的：它用 Spectre.Console 反复重绘进度行。当输出被重定向到管道
（GUI 场景）时，行为与"按行读"的直觉完全不同。本机实测（内核 0.6.0+df70f0b，macOS 15.7，
`--no-ansi-color`，stdout 重定向到文件）得到的硬事实：

1. **进度帧之间没有分隔符**：4623 字节样本中只有 **8 个 `\n`**、**0 个 `\r`**。
   相邻进度帧是首尾直接拼接的：`…--:--:--Vid Kbps ━━━━━… 0/1 0.00% -0.00Bps --:--:--Vid Kbps …`。
2. **日志行之间也会粘连**：`Content Matched: HTTP Live Streaming16:15:07.223 INFO : Parsing streams...`
   前一行的消息没有换行就直接接上下一个时间戳。
3. **仍有 ANSI 转义**：样本中含 ESC 字节（结尾形如 `ESC[?12l`、`ESC[?25h`），不能假设已干净。
4. **字段会缺位、会为负**：`0/1 0.00% -0.00Bps --:--:--`——字节字段整段缺失，百分比与速度带负号，
   ETA 为 `--:--:--`；重试时速度列出现 `(1)` `(2)` 后缀。
5. 日志与进度全部走 **stdout**；.NET 未捕获异常栈走 **stderr**（不可解析，整段记为一条 ERROR）。
6. 上游是 Beta 软件（构建日期 20260628），**输出格式无任何稳定性承诺**。

## Decision

解析层 = **ANSI 剥离 → UTF-8 增量解码 → 时间戳 lookahead 切分 → 日志行解析 + 进度帧提取 → 阶段状态机**，
且 **终态以进程退出码为准**。

### 1. ANSI 剥离（OutputNormalizer）

先全局替换 `/\u{1B}\[[0-9;?]*[a-zA-Z]/` 为空，再进入后续流程。

### 2. UTF-8 增量解码

进度条 `━`(U+2501) 是 3 字节，可能跨 chunk 截断。保留最多 3 字节的尾部残留与下一批拼接；
进程结束时 `OutputParser.flushTail()` 冲刷残留。**严禁**出现替换字符 `�` 或丢帧。

### 3. 时间戳 lookahead 切分（RecordSplitter）

```
(?=\d{2}:\d{2}:\d{2}\.\d{3}\s+(?:INFO|WARN|DEBUG|ERROR)\s*:)
```

零宽断言切分，不吞掉任何字符。切分后每个 record 形如
`<时间戳> <级别> : <消息><粘连的 0..N 个进度帧>`。
第一个时间戳之前的残留（半个进度帧）丢弃。

> 用 `NSRegularExpression` 实现，**不用 Swift Regex DSL**：Regex 的运行时可用性约束会给
> macOS 13 部署目标带来额外风险，而 NSRegularExpression 无此问题且性能足够。

### 4. 日志行解析（LogLineParser）

record 头部匹配（`.dotMatchesLineSeparators = true`）：
`^(\d{2}:\d{2}:\d{2}\.\d{3})\s+(INFO|WARN|DEBUG|ERROR)\s*:\s*(.*)$`
捕获组 3 的**剩余文本**交给 ProgressParser。

### 5. 进度帧提取（ProgressParser）

在 record 剩余文本中全局匹配 progressFrame 正则（见 `kernel-output-contract.md` §3），
按出现顺序以 `name` 为 key 写入字典（后者覆盖前者）→ 每个轨道自然得到本批最新帧。
`-mt` 并发下载时同批出现多个轨道，该规则天然正确。

**两条经实测修正、不得回退的细节**：

1. 轨道名 `name` 必须**以字母开头**且字符集排除 `.` 与 `:`。否则粘连文本会被吞进轨道名
   （实测会捕获出 `Start downloading...Vid Kbps`、`--:--:--Vid Kbps` 这类假名字）。
2. 上游**首个进度帧会把轨道名重复输出一次**（`Vid KbpsVid Kbps`），产生一个永不更新的幽灵轨道。
   对策：`staleWindow = 10` tick 的过期剔除 + 终态 `freeze()` 冻结（契约文档 §4.1）。

鲁棒性要求：百分比 `-0.00` clamp 到 `[0,100]`；速度负值标记 `speedUnknown`；
ETA `--:--:--` 解析为 `nil`；字节字段缺失解析为 `nil`；`(N)` 解析为 `retryCount`。

### 6. 阶段状态机（OutputParser）

| 触发 | 阶段 |
|---|---|
| `Loading URL:` / 首条日志 | `.preparing` |
| `Start downloading...` | `.downloading` |
| 含 `ffmpeg merging` / `Merging` / `Decrypting` | `.merging` |
| 进程退出码 0 | `.finished(.succeeded)` |
| 退出码非 0 | `.finished(.failed)` |
| 用户取消 | `.finished(.cancelled)` |

**关键词只用于展示与阶段提示，绝不用于判定终态。** 终态一律由退出码决定——
否则上游改一个词（Beta 软件完全可能）就会导致任务永远卡在"下载中"，
这正是最贵的"沉默逻辑错误"。

### 7. 失败隔离（最重要的一条）

解析层**禁止抛出异常影响任务生命周期**。任何解析失败：
记一条 `WARN` 日志 + 跳过该段。上游换格式的最坏后果是"界面显示不全"，
绝不能是"下载被打断"。

### 8. 节流与背压

- 必须**持续读取**管道。停止读取会让内核写阻塞进而拖慢下载——这也是 ADR-003 否决
  "停止读取管道"作为暂停手段的原因。
- 进度向主线程发布**节流 ≤ 10 Hz**（100 ms 合并窗口）；日志经 `RingBuffer` 上限 5000 条/任务。

## Consequences

**正面**

- 在实测样本上可完整还原日志与进度，粘连问题被 lookahead 切分彻底解决。
- 终态由退出码判定 + 解析失败隔离，使"上游格式变动"的爆炸半径限制在显示层。
- 纯函数、无 I/O 的解析层可被命令行测试可执行文件完整覆盖（ADR-006），无需真起内核进程。

**负面 / 已知限制**

- 若两条轨道的 `name` 完全相同（罕见），进度归属会串台——接受，UI 不做区分（风险 R5）。
- 切分依赖"时间戳一定出现在行首"这一约定；若上游某天给时间戳换个位置，需要更新
  `ParserPatterns` 中的单一常量（集中在一处，改动面可控）。
- lookahead 切分是 O(n) 但正则开销不低；在 10 Hz 节流下完全够用，
  无需引入 mach 级优化。

## 验证方式

`Tests/Fixtures/kernel_progress_glued.txt`（真实抓取）驱动 `ParserTests`：
断言日志条数 == 时间戳个数（8）、进度帧可解析、`--:--:--` → nil、负值 → unknown、
半行 UTF-8 跨 chunk 与整块解析结果一致。
**变异加固**：把 lookahead 正则改成普通匹配后，「粘连日志切分」用例必须变红。
