# ADR-003: 暂停/继续的实现策略

## Status

Accepted（2026-09-28）

## Background

用户明确要求"暂停 / 继续 / 取消"。但 **N_m3u8DL-RE 没有任何暂停参数**（全部参数见
`docs/contracts/cli-argument-contract.md`，无 pause/resume/suspend 相关项）。暂停必须由 GUI 侧实现。

候选方案：

| 候选 | 机制 | 评估 |
|---|---|---|
| **A. SIGSTOP / SIGCONT 挂停进程组** | `killpg(pgid, SIGSTOP)` 冻结整个进程树 | 即时、零数据损失；但见下方代价 |
| **B. 停止读取管道** | 暂停读 stdout，让内核写阻塞 | **否决**：只会把内核的日志线程堵住，下载线程继续跑，不是暂停；且管道写满后内核整体卡死，恢复时行为不可预期 |
| **C. 终止进程 + 同参数重启（依赖上游续跑）** | kill 后用完全相同的 argv 重启，上游复用 tmp 目录 | 可支撑任意长暂停；但依赖上游未公开承诺的"跳过已下载分片"行为，且需重新解析清单 |
| **D. 不支持暂停，只做取消** | — | 否决：直接违背用户明确需求 |

### 本机实测（本决策的依据）

1. `posix_spawn` + `POSIX_SPAWN_SETPGROUP` 建立独立进程组，`killpg(pid, SIGSTOP)` 返回 0。
2. 挂停验证：spawn `/bin/sleep 4` 后立刻 SIGSTOP，等待 6 秒 —— 进程仍然存活
   （若未挂停，`sleep 4` 早已退出）。SIGCONT 后正常退出，退出码 0。**A 方案机制确认可用。**
3. Swift 中 `WIFEXITED` / `WEXITSTATUS` 宏**不可用**（function-like macros not supported），
   退出状态必须手工解码：`signal = status & 0x7f`；`code = (status >> 8) & 0xff`。
4. `waitpid` 不带 `WUNTRACED` 时不会被 SIGSTOP 打扰，无需特殊处理。
5. 上游 `--http-request-timeout` 默认 **100 秒**（实测 `--help`）；`--download-retry-count` 默认 3。

## Decision

**双策略（A 为主、C 为兜底）+ 时长守卫 + 直播例外。**

### P1（默认）：SIGSTOP / SIGCONT 挂停整个进程组

- `ProcessSpawner` 必须用 `posix_spawn` 且设置 `POSIX_SPAWN_SETPGROUP`（新 pgid = 子进程 pid），
  **禁止**用 `Foundation.Process` 后在父进程补调 `setpgid`（存在 fork/exec 竞态，会静默失败）。
- 暂停 `killpg(pgid, SIGSTOP)`；继续 `killpg(pgid, SIGCONT)`。子进程（ffmpeg 合并、解密）在同一进程组，一并冻结。
- UI 文案：暂停状态显示为"已暂停（进程已挂起）"。

### 时长守卫（P1 → P2 自动转换）

**问题**：SIGSTOP 期间挂起的 .NET 定时器不会推进，但**墙钟在走**。若暂停时长超过
`--http-request-timeout`（默认 100 s），恢复瞬间所有在途 HTTP 请求会被判定超时，
集中触发重试；若反复长暂停，可能耗尽重试次数导致分片失败。

**对策**：`PauseController` 在暂停开始时刻启动一个
`min(httpRequestTimeout × 0.8, 80 s)` 的定时器：

- 定时器触发时任务仍处于暂停 → 先 `SIGCONT` 再 `SIGTERM`（停止中的进程收不到信号，必须先 CONT），
  5 秒后仍未退出则 `SIGKILL` 整个进程组；任务转为 `.stopped(reusable: true)`，
  **保留 tmp 目录**。
- 用户点"继续"时用**完全相同的 argv** 重启（`--save-name` / `--save-dir` / `--tmp-dir` 必须与首次一致，
  这是上游能否复用已下载分片的前提）。
- 高级设置中暴露 `--http-request-timeout`，用户调大即可延长可安全暂停的时长。

### P2（显式）：停止并保留进度

- 用户主动点"停止"（区别于"取消"）：走上述 `SIGCONT → SIGTERM → (5s) → SIGKILL` 路径，保留 tmp。
- UI 提供"重试（保留已下载分片）"按钮。
- **不承诺"断点续传"**：上游未公开保证会跳过 tmp 中已存在的分片。UI 文案写作
  "重试（保留已下载分片）"，禁止写"断点续传"/"继续下载"。
  若实测发现上游确实复用，则在 CHANGELOG 中升级文案——这是唯一允许的措辞升级路径。

### 取消

`SIGCONT → SIGTERM → 5s → SIGKILL(pgid)`。默认按设置 `deleteTempOnCancel`（默认 true）清理 tmp 目录。
**必须 killpg 而不是 kill**：ffmpeg / mp4decrypt 是内核的子进程，只 kill 父进程会留下孤儿。

### 直播任务例外

直播（未开 `--live-perform-as-vod`）**禁用暂停**：SIGSTOP 期间播放列表持续刷新，恢复后必然丢片段，
且上游直播录制本身建议一次性完成。UI 上直播任务的暂停按钮降级为"停止"（图标 `stop.fill`）。

### 应用退出

`AppDelegate.applicationWillTerminate` 中对所有运行中的任务执行"停止并保留"（不删 tmp），
避免留下孤儿进程。**不做**跨启动的自动恢复：下次启动只展示历史记录，由用户手动重试。

## Consequences

**正面**

- 满足用户明确需求，且常规时长暂停（< 80 s）**零数据损失、零额外开销、恢复即时**。
- 时长守卫把"长暂停导致重试雪崩"这一最坏情况收敛为一次可预期的自动停止。
- 进程组语义让取消/清理彻底，无孤儿进程。
- 全部机制已在本机实测验证（见 Background）。

**负面 / 代价**

- 暂停语义不完美：> 80 s 的暂停会自动变成"停止"，用户需要再点一次继续（会重新解析清单，约 1–3 s）。
  这是与上游无暂停 API 的必然妥协。
- P2 是否有效复用已下载分片**未在本机验证**（需联网真实流）。故不写入产品承诺。
- `posix_spawn` + 管道需自行用 `posix_spawn_file_actions_adddup2` 搭建，`ProcessSpawner` 是全项目
  唯一接触 Darwin 进程 API 的地方（约 180 行），复杂度集中、可测。
- 暂停期间 UI 的"已用时长"必须扣除暂停时长，否则统计失真（PauseController 负责记账）。

## 验证方式

- 单元测试：`PauseControllerTests` 用 `ProcessControlling` 协议替身断言
  "超时后调用了 terminate 而非 resume"、"直播任务 pause 走 stop"。
- 集成测试（`--include-integration`，CI 不跑）：真起 `/bin/sleep` 进程组，断言暂停后 6 s 仍存活、
  恢复后正常退出（即 Background 第 2 条的脚本化版本）。
